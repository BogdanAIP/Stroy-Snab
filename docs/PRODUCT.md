# Product

## Цель

Stroy-Snab — проверяемый агент строительных закупок для русскоязычной практики снабжения.

Он должен уметь принимать реальные закупочные документы и заявки, превращать их в структурированные позиции, находить и сопоставлять товары/поставщиков, отделять точное совпадение от потенциального аналога, сравнивать коммерческие условия, готовить закупочное решение и позднее безопасно исполнять подтверждённые действия через CAP и внешние системы.

## Базовый пользовательский поток

```text
документ / заявка / спецификация
 -> структурированные позиции
 -> нормализация
 -> exact/candidate matching
 -> supplier discovery / offers
 -> comparison + evidence
 -> recommendation
 -> human approval where required
 -> verified execution
```

## Принципы продукта

1. `evidence-first`: каждое существенное утверждение о товаре, поставщике, цене, наличии, стандарте или результате действия должно иметь источник.
2. `reuse-first`: mature OSS/open data/API раньше собственного движка.
3. `false-equivalent minimization`: лучше `CANDIDATE/UNKNOWN`, чем ложный технический аналог.
4. `human authority`: проектные/технические замены и реальные заказы требуют явно определённой authority policy.
5. `CAP composition`: Stroy-Snab использует CAP как внешний trusted execution/verification layer, а не копирует его.
6. `real-data evaluation`: качество оценивается на реальных закрытых документах и разрешённых обезличенных fixtures, а не только на искусственных примерах.

## Не-цели ранних стадий

- не строить собственную ERP/PIM до доказанного пробела;
- не создавать полный каталог ГОСТ/ТУ/DIN;
- не строить собственную LLM/browser runtime;
- не автоматизировать реальную оплату или безусловное размещение заказов;
- не обещать универсальную техническую взаимозаменяемость материалов;
- не загружать закрытые пользовательские документы в публичный GitHub.

## Первый полезный результат

Первая ценная версия должна надёжно выполнить цепочку:

```text
УПД/счёт/спецификация
 -> строки товаров
 -> поставщик + документ + единицы + количество
 -> канонические товарные признаки
 -> повторяющиеся/похожие позиции между документами
 -> оценка качества извлечения и нормализации
```

Только после доказанного качества этого слоя проект переходит к поиску внешних предложений и автономным закупочным действиям.
