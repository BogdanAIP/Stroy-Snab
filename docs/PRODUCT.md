# Product

## Цель

Stroy-Snab — проверяемый агент строительных закупок для русскоязычной практики снабжения.

Он должен уметь принимать реальные закупочные документы и заявки, превращать их в структурированные позиции, восстанавливать связи между потребностью, коммерческими документами, поставками и входным контролем, находить и сопоставлять товары/поставщиков, отделять точное совпадение от потенциального аналога, сравнивать коммерческие условия, готовить закупочное решение и позднее безопасно исполнять подтверждённые действия через CAP и внешние системы.

## Базовый пользовательский поток

```text
заявка / спецификация
 -> структурированные позиции
 -> нормализация
 -> supplier discovery / offers
 -> comparison + evidence
 -> recommendation
 -> human approval where required
 -> verified execution
 -> счёт / УПД / поставка
 -> входной контроль / фактическое исполнение
 -> сверка с исходной потребностью
```

Реальный процесс не предполагает соответствия 1:1 между строками документов. Одна позиция может быть разбита между несколькими счетами/поставками, несколько строк могут быть объединены, возможны дозаказы, частичные и сверхпоставки, замены и незакрытые позиции.

## Принципы продукта

1. `evidence-first`: каждое существенное утверждение о товаре, поставщике, цене, наличии, стандарте, связи документов или результате действия должно иметь источник.
2. `reuse-first`: mature OSS/open data/API раньше собственного движка.
3. `false-equivalent minimization`: лучше `CANDIDATE/UNKNOWN`, чем ложный технический аналог.
4. `human authority`: проектные/технические замены и реальные заказы требуют явно определённой authority policy.
5. `CAP composition`: Stroy-Snab использует CAP как внешний trusted execution/verification layer, а не копирует его.
6. `real-data evaluation`: качество оценивается на реальных обезличенных документах и разрешённых fixtures, а не только на искусственных примерах.
7. `lifecycle over pair matching`: продукт моделирует закупочный процесс как граф доказанных связей между документами и строками, а не как пары `заявка = УПД`.

## Не-цели ранних стадий

- не строить собственную ERP/PIM до доказанного пробела;
- не создавать полный каталог ГОСТ/ТУ/DIN;
- не строить собственную LLM/browser runtime;
- не автоматизировать реальную оплату или безусловное размещение заказов;
- не обещать универсальную техническую взаимозаменяемость материалов;
- не загружать сырые закрытые пользовательские документы в публичный GitHub.

## Первый полезный результат

Первая ценная версия должна надёжно выполнить цепочку:

```text
заявка / счёт / УПД / спецификация / входной контроль
 -> строки товаров
 -> роль документа + единицы + количество
 -> доказанные и candidate связи между документами
 -> канонические товарные признаки
 -> повторяющиеся/похожие позиции
 -> частичное/полное/сверх исполнение там, где это доказуемо
 -> оценка качества извлечения, linkage и нормализации
```

Только после доказанного качества этого слоя проект переходит к поиску внешних предложений и автономным закупочным действиям.
